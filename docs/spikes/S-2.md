# S-2 — Overlays, docks and per-widget origins in OBS (DEN-3)

- **Date:** 2026-10-18 · **Agent:** claude/claude-opus-5-5 · **Card:** DEN-3
- **Status:** Linux (E-1, Hyprland) **done**. Windows VM (E-3) **pending owner approval**. See [Not tested](#not-tested--pending).
- **Code:** [`spikes/S-2-obs-overlays/`](../../spikes/S-2-obs-overlays/) (throwaway). **Evidence images:** [`docs/spikes/S-2/`](S-2/).

## TL;DR

1. Overlays served by axum on `127.0.0.1` render **transparent** in OBS browser sources. Events arrive in about 1 ms, and a
   backoff client reconnects within the backoff cap (≤ 5 s) after the server restarts.
2. **Docks:** native Wayland OBS has **no custom browser docks at all**. The menu item is missing and a seeded dock is
   never created. Under XWayland the same seeded dock appears, renders, and streams chat. Q-U5 (native chat window
   on Wayland) is confirmed.
3. **Per-widget origins work** in OBS's CEF. `w-<id>.localhost` resolves inside CEF, is a secure context, and
   localStorage/IndexedDB/cookies are **isolated per widget** and **persist** across refresh, source re-create and OBS
   restarts. Use `http://w-<id>.localhost:<port>/`, not distinct ports, because cookies leak across ports.
4. **Chromium LNA is enforced** in this OBS build (Arch: obs-browser on system CEF 152). A **public** page can't reach
   `127.0.0.1`/`localhost`/`*.localhost`: it is blocked silently, with no prompt. Loopback-to-loopback is unaffected.
5. SE-style widget: Google Fonts (link and `@import`), jQuery and GSAP from public CDNs all load from a widget origin.
6. **Biggest practical risk (NVIDIA on Linux):** with the default *Browser Source Hardware Acceleration* on, browser
   sources render **blank** on native Wayland and **crash OBS** under XWayland. Turning it off fixes both. Fresh Arch
   OBS profiles also show a blocking **"Chromium Additional Terms of Service"** dialog until it is accepted.

### What was run

2. `target/release/s2-obs-overlays --port 47800 --data /tmp/den-s2/data` starts the server. Every client report, probe hit
   and WebSocket event is appended to `reports.jsonl` and served at `GET /report`.
3. `scripts/launch-obs.sh /tmp/den-s2-obs <wayland|xcb> <log>`, then `node driver/s2.mjs setup 47800 <run>` creates scene

4. `driver/s2.mjs refresh|recreate|seturl|add|shot` drives `refreshnocache`, re-create, URL changes and

5. Window evidence: `hyprctl clients -j` gives the OBS window rectangle, then `grim -g` captures that region only.

### LNA / private-network details (check 4)

- Loopback page → loopback (same-origin, `*.localhost` → `127.0.0.1` cross-origin, `fetch` with preflight, `<img>`, WS):
  no prompt, no block, and **no** `Access-Control-Request-Private-Network`/LNA headers on preflights.
- Public page → loopback: an `https://example.com/` browser source (and `http://example.com/`, which is HSTS-upgraded) was
  given OBS *Custom CSS* whose background images point at `127.0.0.1`, `localhost` and `w-lna.localhost`. **All 6
  requests were blocked before reaching the server.** OBS log: `Access to image at 'http://127.0.0.1:47800/…' from
  origin 'https://example.com' has been blocked by CORS policy: Permission was denied for this request to access the
  'loopback' address space.` No prompt is shown (off-screen browser), so the failure is **silent** except in the OBS log.
- Why: this obs-browser (32.2.2) lacks upstream's "temporary" loopback auto-grant (obs-browser `058c30f`, see tech-stack
  §8), but Arch runs it on Chromium 152, where LNA is enforced.

### Control endpoints vs widget origins (review fix, 2026-10-18)

The Codex review found that a widget could inject alerts: `http://w-a.localhost:<port>` sent a simple `text/plain`
POST to the app's `/emit` and the overlay showed it, and foreign Origins got 200 too. Both origins are loopback, so LNA
does not apply, and CORS only hides the response, not the side effect of a simple POST. Host-header routing alone was
not enough, because the *destination* Host is the app's.

Fix in the spike: `/emit` and `/api/chat` now require an app Host **and** an `Origin` that is exactly
`http://127.0.0.1:<app-port>` or `http://localhost:<app-port>`, or no `Origin` at all (curl and scripts; Chromium always
sends `Origin` on POST). Widget origins (`w-<id>.localhost`, distinct widget ports), foreign origins, `null` and any
`Sec-Fetch-Site` other than `same-origin`/`none` get **403**, are logged as `server.control_rejected`, and publish no
event. Permissive CORS stays only on `/report` and `/probe/*`. WebSocket upgrades still accept widget origins
(widgets need their own event socket) but reject `null` and foreign origins.

Evidence (`scripts/origin-check.sh`, own server on port 47931, data under `/tmp`):

- Before the fix (binary from `26f76ba`): 8 of 18 curl cases failed. Widget, foreign, `null` and cross-site POSTs to `/emit`, and widget and cross-site POSTs to `/api/chat`, all
  returned 200 and published an event.
- After the fix: 18/18 pass. CLI and both app origins get 200 with one event each. Widget, widget without fetch metadata,
  foreign, `null`, cross-site `Sec-Fetch-Site` and widget Host get 403 with no event, and there are 12
  `server.control_rejected` entries.
- With `CHROME=/usr/bin/chromium` (headless, throwaway profile): a real `w-a.localhost` page's `no-cors` POSTs to both
  endpoints published **0** events (2 rejections logged), and the `/dock/chat` page's same-origin JSON fetches (as in `dock.html`) returned 200 and published 2.
- `cargo test`: 2 unit tests for the origin policy pass.

## Recommendations

### 1. Per-widget origin scheme

- **Adopt `http://w-<id>.localhost:<port>/` on the single app port** (Host-header routing), as proposed in
  se-widget-compat A6.3. It gives a real, secure, persistent origin per widget with separate localStorage, IndexedDB
  **and cookies**.
- **Use distinct ports only as a fallback.** Cookies are shared across every port of `127.0.0.1` (including the app's
  own origin), each widget costs a listening port, and ports collide: during this spike another app already held 47811.
- **Validate Host strictly**: accept only `127.0.0.1:<p>`, `localhost:<p>` and `w-<id>.localhost:<p>`, otherwise return
  421 (done in the spike). Check `Origin` on WS upgrades and reject `null`.
- **Gate every control and mutating endpoint on `Origin`, not just Host**: accept only the app's own origins (or no
  `Origin` for local CLI clients), and reject widget origins, `null` and foreign origins with 403. Widget code is
  untrusted and lives on loopback, so neither LNA nor CORS protects these endpoints (see the review fix above). Widgets
  get a separate, narrower API.
- `<id>` is a DNS label: `[a-z0-9-]`, ≤ 63 characters. Use a stable per-instance hash so storage survives renames.
- **Plan for storage partitioning.** An iframed widget's storage is keyed by the top-level site, so the same widget
  sees **different localStorage in the OBS overlay than in a StreamDen preview window**. So: (a) always use the same
  overlay host (`127.0.0.1`, never mix with `localhost`); (b) back the SE `localStorage` shim with **per-widget KV on the
  server**, write-through and hydrated before widget code runs, in **all** modes, not only fallback. That also fixes the
  crash-loss finding.
- Widgets must not depend on cookies: they aren't stored in the iframe context.
- The opaque-sandbox iframe option is confirmed broken for SE parity (every storage API throws).
- Bind `::1` as well as `127.0.0.1` on the same port. CEF didn't need it, but the system resolver maps `*.localhost`
  to `::1`, so curl, other browsers and tools would otherwise fail.

### 2. Dock strategy

- **Ship both:** the OBS dock URL (`/dock/chat`) **and** a native StreamDen always-on-top chat window (Q-U5). On native
  Wayland, OBS offers no custom browser docks at all, so the native window is the only in-OBS-workflow option there.
- **Tell Wayland users:** "OBS hides *Custom Browser Docks* on native Wayland. Use StreamDen's chat window, or start OBS
  under XWayland (`QT_QPA_PLATFORM=xcb obs`). **On NVIDIA, also turn off Settings → Advanced → Sources → Browser Source
  Hardware Acceleration**, or browser sources may be blank (Wayland) or OBS may crash on start (XWayland)." Show this in
  the UI and docs, and never edit the user's OBS config ourselves.
- Dock entries survive switching between Wayland and XWayland sessions (the `ExtraBrowserDocks` JSON in `user.ini`
  `[BasicWindow]`, OBS ≥ 31), so XWayland users only add the dock once.
- Docks must talk only to our HTTP/WS API. `window.obsstudio` exists in docks, but its callbacks did not fire.
- OBS can't add docks over obs-websocket. Offer a "copy dock URL" button with click-by-click steps.

### 3. Reconnect and backoff defaults (validated)

- Client: base **250 ms**, ×2, cap **5 s**, equal jitter (`d/2 + rand·d/2`). Reset on open.
- Server heartbeat every **5 s**. The client watchdog closes and reconnects after **12.5 s** of silence.
- Resume with `?last=<eventId>` against a server-side ring buffer (200 events), and dedupe by event id.
- Overlays never show a reconnecting state (debug flag only). Docks may.
- Expected recovery after the core returns: ≤ 5 s (measured 0.14–3.2 s).
- The SE runtime must use the **same** reconnecting client. The spike's minimal SE shim did not reconnect.

### 4. CEF limitations that affect the StreamElements widget runtime

1. **LNA:** anything loaded from a public origin (hosted SE overlay URLs, GitHub-Pages widgets that open
   `ws://127.0.0.1`) **cannot reach StreamDen** in Chromium ≥ 142 builds without the OBS auto-grant (seen here). Upstream
   OBS 33 auto-grants "temporarily". Behaviour depends on the OBS build and distro, so rely on neither: **always serve
   widgets from our loopback origin** (confirms the tech-stack §8 rule). Loopback → public CDN loads are unaffected.
2. **Storage partitioning** and **no iframe cookies** (see §1).
3. **localStorage can lose the last seconds of writes** on a CEF crash. Server-backed KV is the durable store.
4. **NVIDIA + Linux hardware acceleration:** blank or crashing browser sources. Our overlay runtime must render well in
   software (CSS transforms and opacity, no WebGL, modest blur). That is already a rule, and these results make it a requirement.
5. **First-run ToS dialog** (Chrome-runtime CEF, Arch builds): blank sources on a fresh OBS profile until a
   "Chromium Additional Terms of Service" window is accepted. Add to troubleshooting.
6. `window.obsstudio` works in browser sources (control level 1, *ReadObs*, by default), but not reliably in docks.

## Spike code and gotchas

- `src/main.rs` is the axum server (Host routing, `/report`, `/emit`, `/api/chat`, `/probe/*`, `/ws` with heartbeat and
  resume, distinct-port listeners via `--widget-ports`). `assets/*.html` holds the overlay, dock, widget probe, iframe host
  and SE sample. `driver/s2.mjs` is a zero-dependency obs-websocket v5 client (Node ≥ 22 global `WebSocket`). `scripts/`
  holds the config seeding, isolated launch and restart measurement.
- `cargo clippy --release -- -D warnings` is clean, with no `allow`s. `cargo test` covers the control-origin policy.
- `scripts/origin-check.sh` is the control-origin regression (run `cargo build --release` first; needs curl and `jq`).
  It runs curl cases, plus a headless-Chromium pass via `driver/origin-browser.mjs` when `CHROME` is set.
- New crates (spike only): axum 0.8 (MIT), tokio 1 (MIT), serde_json 1 (MIT/Apache-2.0). The sample widget loads jQuery
  (MIT) and GSAP (GreenSock "standard" license, runtime CDN load only, never vendored) to mimic real SE widgets.
- Hyprland 0.56 uses Lua dispatchers: `hyprctl dispatch 'hl.dsp.send_shortcut({ mods = "ALT", key = "d", window =
  "address:0x…" })'`. The old `dispatch sendshortcut …` syntax fails.
- `obs --multi` plus `XDG_*` under `/tmp` gives a fully isolated OBS. Close it with `hl.dsp.window.close` so CEF
  flushes storage. Use `pkill -x s2-obs-overlays`, not `pkill -f`, because the pattern can match the calling shell.
