# S-1 — Tauri 2 shell reliability on Hyprland + NVIDIA (DEN-2)

- **Date:** 2026-10-18 · **Agent:** claude/claude-opus-5-5 · **Card:** DEN-2
- **Code:** [`spikes/S-1-tauri-shell/`](../../spikes/S-1-tauri-shell/) (throwaway)
- **Evidence:** screenshots and raw numbers in [`docs/spikes/S-1/`](S-1/) (`measurements.json`)
- **Status:** E-1 done. **E-2 (CachyOS KDE) and E-3 (Windows VM) are pending owner approval.**

## TL;DR

**Go for Tauri 2, with conditions.** On E-1, the owner's Hyprland + NVIDIA desktop, the default
configuration (level 0, no env vars, no quirk) rendered correctly every time. There was no blank window, no
`Error 71`, no DMA-BUF framebuffer error and no crash. First paint took about 250 ms and idle CPU was under 1 %.
Tray, close-to-tray with recreate, a second window and the crash-loop fallback all work.

Four things must change before the plan relies on these results:

1. **Don't enable the early-GL-context quirk by default.** On this machine it makes GTK paint every frame
   through Mesa's software rasterizer (llvmpipe). That costs 5× the CPU in a window and about 4.5 cores
   fullscreen (§4).
2. **Closing a Tauri window does not end its `WebKitWebProcess`.** Each close and reopen leaks about 100–130 MB
   until the app exits. The spike's fix terminates the web process before destroying the window (§6).
3. **Even with that fix, the in-process shell keeps about 196 MB PSS while closed to tray.** The engine alone
   needs about 52 MB. Reaching the §11.3 target ("under 150 MB with the UI closed") means the UI has to live
   in its own process (§9).
4. **`always_on_top` is ignored on Hyprland**, on native Wayland and on XWayland alike. Use compositor rules
   (Hyprland `pin`) or an OBS dock for the chat window (§7).

**Caveat on coverage.** On E-1, WebKit renders on the **AMD iGPU**, not on the NVIDIA GPU (§4), so a pure
NVIDIA-only Linux desktop is still untested. Re-check on E-2, and if possible on a machine without an iGPU,
before the owner accepts ADR-0002.

## 2. What the spike contains

`spikes/S-1-tauri-shell/` holds a Vite + React + TS page (CSS animation plus an engine status panel), a chat
mock page, and a Rust backend:

- **Engine stand-in:** a Tokio task ticks once per second, emits `engine-tick` to webviews, sends it to
  browsers over SSE and appends to `engine.log`. It never depends on a window.
- **Shell:** the tray (Show / Hide to tray (destroy webview) / Second window (chat) / Open UI in browser /
  Quit) and close-to-tray. `ExitRequested` is prevented when the last window closes. Windows are recreated on
  demand, and the chat window asks for `always_on_top(true)`.
- **Local server** (axum, `127.0.0.1` only, Host and Origin guard): serves the same UI to a browser, plus
  `/api/state`, `/api/ticks` (SSE) and, with `--test-control`, `/api/test/{action}` for scripted tests.
- **Graphics-compat ladder:** chosen by `--compat-level N` or the persisted level file, and applied with
  `set_var` at the top of `main()`, before any thread or GTK init. The vars affect this process and its
  WebKit children only.

  | Level | Sets |
  |---|---|
  | 0 | nothing |
  | 1 | registers `tauri-plugin-wayland-nvidia-quirk` (early GL context) |
  | 2 | `WEBKIT_DISABLE_DMABUF_RENDERER=1` |
  | 3 | level 2 + `WEBKIT_DISABLE_COMPOSITING_MODE=1` |
  | 4 | `GDK_BACKEND=x11` |
  | 5 | browser fallback (no webview) |

- **Crash-loop detection:**
  1. Write `starting.json` before the webview is created.
  2. The page reports first paint through `invoke("first_paint")` after two `requestAnimationFrame`s, and the
     marker is deleted then.
  3. If the marker is still there at the next start (and its PID is dead), move one level up and persist it.
  4. Past level 4, fall back to the browser UI.

  `--reset-compat` clears this state, and `--no-first-paint-ack` simulates a window that never paints.

Run it: `npm ci && npm run build && (cd src-tauri && cargo build --release)`, then
`scripts/launch.sh <run-dir> -- --compat-level 0 --state-dir <run-dir>/state --test-control`.
`scripts/matrix.sh`, `crashloop.sh`, `cycle.sh`, `tray.sh` and `measure.py` reproduce the tables below.

Other observations:

- At level 4 the Omarchy session's `GDK_SCALE=2` takes effect, because Hyprland uses
  `xwayland.force_zero_scaling`. The page renders at 2× and shows a 500×360 CSS viewport in a 1000×720
  window. On native Wayland (levels 0–3), GTK ignores it and the device pixel ratio stays at 1.
- At levels 2 and 3 the numbers are identical. With DMA-BUF off, WebKit 2.54 already uses the SHM path, so
  the extra no-compositing switch changes nothing visible here. These levels are cheaper for this simple page,
  but they mean CPU painting, which will cost more for a busy designer canvas.

## 4. Root cause: which GPU actually renders

- **`WebKitWebProcess` renders on the AMD iGPU.** It holds `/dev/dri/renderD129`, which is `amdgpu`, through
  Mesa. It first tries the NVIDIA node through Mesa EGL, which fails and produces the
  `MESA-EGL … 10de … failed to create dri2 screen` lines, then picks the iGPU. Hyprland runs on NVIDIA and
  composites the cross-GPU DMA-BUFs without complaint.
- **The UI process's GTK3 GL ends up on Mesa llvmpipe (software).** 32 `llvmpipe-N` threads are loaded at
  every Wayland level. When glvnd is forced to NVIDIA's EGL vendor, GTK's GL initialisation fails entirely.
- **What follows from this:**
  - The **early-GL-context quirk** (and `GDK_GL=always`) makes GTK paint *every frame* with llvmpipe. Per-thread
    sampling shows `llvmpipe-*` at 334 % CPU fullscreen. The plugin still reports `Applied { gpu: 0x10de }`,
    because it detects the NVIDIA GPU, not which GL implementation GTK actually got.
    **Don't enable it by default.** Keep it as an explicit opt-in level, and re-evaluate on an NVIDIA-only
    machine, where its premise (NVIDIA EGL in the UI process) might hold.
  - E-1 does **not** exercise the "WebKit renders on NVIDIA" path that the field reports (§4.1 of the
    research) describe, because the iGPU takes over. A pure-NVIDIA Linux desktop is still a test gap. On this
    machine the risk is really "hybrid laptop/desktop" behaviour, which looks fine.

## 6. Tray, close-to-tray, engine

- **Tray: ✅.** The item registers with the `StatusNotifierWatcher` that the Omarchy shell (quickshell) owns;
  status is `Active`, and all 6 menu entries are exported over dbusmenu. Show, Hide, Second window and Quit
  all worked when clicked over D-Bus the way the bar host does it.
  - ⚠️ The Omarchy bar puts unpinned tray items in a collapsed drawer behind a `<` chevron. Without pointer
    injection the agent couldn't open it to *see* the icon or click it by mouse, so **the owner should do one
    visual and mouse check.**
  - `tray-icon` still links the deprecated libayatana-appindicator3. It works, but prints a warning.
- **Close-to-tray: ✅ for behaviour, ⚠️ for memory.**
  - Behaviour. Tray "Hide", a compositor close (`hl.dsp.window.close`, as with SUPER+W) and the page's button
    all destroy the window. The app stays in the tray. `engine.log` keeps ticking with `webviews=0`, and the
    recreated page shows the continued count ([reopened-after-3-close-cycles.png](S-1/reopened-after-3-close-cycles.png)).
    Reopening to first paint takes **165–210 ms**.
  - **Bug: `WebviewWindow::destroy()` leaves that window's `WebKitWebProcess` running until the app exits**,
    and a reopen spawns a new one. The old one isn't reused. After 3 close/reopen cycles with a plain
    `destroy()`: 4 web processes, **573 MB PSS / 1.39 GB RSS while "closed"**.
  - **Fix in the spike:** `with_webview(|w| w.inner().terminate_web_process())` before `destroy()`, also on
    `CloseRequested`. After 3 cycles there are 0 web processes and closed PSS is 196 MB.
    `--no-terminate-webprocess` reproduces the leak.
- **Quit** from the tray exits the app and all its WebKit children. No orphans were left after `SIGKILL`
  either (§8).

- ❌ **`always_on_top(true)` is not honoured**, on native Wayland and on XWayland (level 4) alike. Tauri

- Plan: document a Hyprland rule (`float`, `pin`, `size`, matched on title or app_id), test KWin's "keep

## 8. Crash-loop fallback (proof)

Clean state dir, no `--compat-level`, the app sent `SIGKILL` 0.1 s after launch (before first paint, which takes
about 250 ms), five times in a row, then started a sixth time:

| Run | Level chosen at start | Why | First paint | Marker after kill |
|---|---|---|---|---|
| 1 | 0 defaults | default | none | present |
| 2 | 1 early-GL quirk | crash-loop: run 1 (level 0) never painted | none | present |
| 3 | 2 no-dmabuf | crash-loop: run 2 never painted | none | present |
| 4 | 3 no-dmabuf+no-compositing | crash-loop: run 3 never painted | none | present |
| 5 | 4 x11 | crash-loop: run 4 never painted | none | present |
| 6 | **5 browser fallback** | crash-loop: run 5 never painted | n/a | none written |

Run 6 checks:

- No window and no WebKit processes.
- `GET /` returns 200 `text/html`, and `/api/state` reports `browser_fallback: true`.
- SSE delivered 3 ticks in 3 s, and the tray menu was still live.
- The same UI rendered in headless Chromium with SSE ticks
  ([browser-fallback-headless-chromium.png](S-1/browser-fallback-headless-chromium.png)).
- Host and Origin guard: a foreign `Host` and a cross-origin `POST` both get 403.

The level persists (`compat-level` = 5) until `--reset-compat`. Other checks:

- After `--reset-compat` the app starts at level 0, paints, and clears the marker. A normal restart stays at
  level 0.
- **Simulated blank window** (`--no-first-paint-ack`): the window opens, the user closes it after 5 s and quits
  from the tray. The next start says "crash-loop: previous run (level 0) never painted" and uses level 1.

Caveats for production:

- The JS ack proves the web process ran and produced a frame. It does **not** prove the compositor showed it:
  a grey surface with live JS would still ack. Keep tray "Open UI in browser" and a CLI flag as manual escapes.
- Bump only after **two** failures within N seconds (research §4.3), so a user's Ctrl+C during startup
  doesn't change the level.
- With the quirk demoted (§4), the ladder should be 0 → no-dmabuf → +no-compositing → x11 → browser.

| State | CPU, % of one core | PSS | RSS |

| Closed to tray, plain `destroy()` (after 3 cycles), 60 s | 0.07 % | 573 MB (4 web processes) | 1,388 MB |
| **Engine + tray only** (browser-fallback mode, no webview ever created), 60 s | **0.00 %** | **52 MB** | **92 MB** |

How this compares with the plan's expectations:

- The research's "≈94 MB idle" (an empty-app CI benchmark) does not hold on this desktop: about 350 MB PSS
  with the window open. That is still at the low end of the 280–590 MB the research quotes for Electron.
- The §11.3 target ("under 150 MB RSS with the UI closed") is **not met in-process**:
  - The UI process keeps about 100–140 MB after its webviews are gone, because of GTK/WebKit/LLVM state and
    the heap.
  - `WebKitNetworkProcess` stays at about 50 MB.
  - The engine + tray process alone is 52 MB PSS / 92 MB RSS. Putting the UI in a separate process that exits
    on close would meet the target.
- The spike's Tokio runtime started **32 worker threads** (one per logical CPU). The real engine should cap
  that.

## 10. Recommendation for ADR-0002

**GO: Tauri 2 stays the shell. Accept it after E-2 and E-3 confirm, and with the changes below.** Tauri 3
CEF and Electron are not needed on this evidence.

- **Why Tauri 2 holds up.** The owner's setup was the one most likely to break, and it rendered by default at
  every level. There was no `Error 71` and no blank window. First paint was about 250 ms, idle CPU under 1 %,
  and the stripped binary is 8.9 MB. Every problem found sits in the thin shell layer and has a fix or a
  workaround. None is a WebKitGTK rendering failure.
- **Why not Tauri 3 CEF.** It is still alpha and adds hundreds of MB, and E-1 shows no rendering problem that
  Chromium would solve. It stays the exit hatch if E-2 or an NVIDIA-only machine shows WebKitGTK failures that
  levels 2–4 can't fix.
- **Why not Electron.** It would also fix nothing seen here. It would not fix the always-on-top issue
  either: Wayland has no protocol for it, so it is compositor policy, not a WebKit limit. It also costs more
  idle memory. It stays the runner-up.

Proposed follow-ups. These need changes outside this card's scope (ADR, architecture, research and the
board), so they go to whoever owns those:

1. **Compat ladder:** the default is level 0. Move the early-GL quirk out of `auto` and make it opt-in. Detect
   GTK's actual GL renderer (llvmpipe) before ever forcing GL painting. Ladder: 0 → no-dmabuf →
   +no-compositing → x11 → browser. Bump on 2 failures.
2. **Shell rule:** closing a webview must terminate its web process (spike fix). Report it upstream to
   wry/Tauri, because `destroy()` leaking `WebKitWebProcess` on Linux is an upstream bug.
3. **Architecture (§11.1):** look at a two-process model. The engine + tray process (`streamdend`-like,
   about 52 MB) stays resident, and the Tauri UI process starts on demand and exits on close. Only that meets
   the §11.3 "UI closed" memory target.
4. **Chat window on Wayland:** don't promise always-on-top. Ship documented Hyprland/KWin rules, and use the
   OBS-dock/browser-source chat as the main path.
5. **Test gap:** WebKit on an NVIDIA-only Linux desktop (no iGPU), plus a monitor-scale change
   (scale 1 ↔ 2). Ask the owner whether E-2 is NVIDIA-only.
6. Cap Tokio worker threads in the engine. Watch for `tray-icon` moving to libayatana-appindicator-glib.
