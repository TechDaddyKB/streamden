| Question | Do the QuickJS sandbox and the Python worker design in [tech-stack §7.2](../research/tech-stack.md#72-recommended-design) meet the latency and safety goals? |

## Verdict

- **Latency: yes, by a wide margin.**
  - A warm JS call costs about 1.3 µs. A cold JS runtime+context costs about 50 µs.
  - A warm Python round trip costs about 23-36 µs. A Python worker becomes ready in 13-16 ms, much less than the 30-80 ms estimate.
- **Python safety: yes.**
  - The soft cancel lands in 1-7 ms.
  - The hard kill and respawn work in every adversarial case (swallowed interrupts, native code holding the GIL, segfaults, `os._exit`, memory bombs).
  - The host was never affected.
- **In-process JS safety: only partly.**
  - The interrupt handler kills JS-bound loops within about 35 µs.
  - The memory and stack limits are clean.
  - But the deadline is **not a hard bound**: a loop of slow *native* calls overshot a 100 ms deadline by 1.9 s and 7 s. In a first run, the overshoot was **415 s**.
  - A QuickJS assertion or native crash aborts the whole host.
- **So the "isolated JS worker" mode is required, not optional.** See the recommendations.

## What was built

- **`JsHost`** (`src/js.rs`):
  - one rquickjs `AsyncRuntime` + `AsyncContext` per host;
  - a 64 MiB memory limit and a 512 KiB stack limit;
  - an interrupt handler that checks a deadline held in an `AtomicU64`.
- **Injected API:**
  - `api.log`, `api.setArg`, and `api.globals.get/set`, backed by a Rust `HashMap` that JS and Python share;
  - an async `api.http.fetch`, which is a Rust future that sleeps 5 ms and returns JSON.
- **Script wrapping and threading:**
  - User code becomes the body of `async function (args)`.
  - The host returns `{ok, setArgs, logs}`. `return false` gives `ok:false`.
  - JS runs on a dedicated OS thread (16 MiB stack) with a current-thread Tokio runtime.
- **Python `Pool`** (`src/py.rs`):
  - N=2 pre-warmed `python3 -I -B den_worker.py` processes;
  - LSP `Content-Length` framing and JSON-RPC 2.0 in both directions.
  - The host sends `execute{code,args}`. The worker sends `globals.get/set` and `log` requests back to the host while the execution is in flight. `print()` lines become `log` notifications.
- **Timeouts:**
  - Soft timeout: `$/cancelRequest`, or SIGINT (both modes measured).
  - Hard timeout: kill after a grace period, then a background respawn.

## Surprises and gotchas

### QuickJS / rquickjs

**G-1. The deadline is tick-based, not time-based.**
- QuickJS-NG calls the interrupt handler every `JS_INTERRUPT_COUNTER_INIT = 10000` ticks (`quickjs.c`). A tick is one function call or one backward jump.
- A loop whose body is a single slow native builtin (`Array#sort`, `String#indexOf` on large strings, and so on) checks the deadline only every ~3,000-5,000 iterations.
- Result: 1.9 s, 7 s, and in one run 415 s past a 100 ms deadline. The kill did eventually happen, but nothing bounds it.
- No public API forces an earlier poll. The counter is a compile-time constant, so changing it means forking `rquickjs-sys`.
- A host thread cannot be killed safely either. **In-process, a runaway script can only be detected, never stopped.**

**G-2. The interrupt handler never sees time spent in `await`.**
- While JS awaits a Rust future, no bytecode runs, so the handler never fires. The host must also wrap the call in `tokio::time::timeout`.
- **Dropping that future leaves the JS continuation alive** in the context's job queue and the rquickjs scheduler. It resumed during the *next* execution and wrote into that execution's logs and `setArgs`: cross-run contamination.
- So after an await timeout the context (better: the runtime) must be thrown away.

**G-3. `Persistent` drop order can abort the process.**
- My first `JsHost` declared `rt` and `ctx` before the cached `Persistent<Function>`. Dropping it made `JS_FreeRuntime` hit `assert(list_empty(&rt->gc_obj_list))` and **abort the whole process**: SIGABRT and a core dump.
- QuickJS assertions are on in release builds. rquickjs has a `disable-assertions` feature, but turning it off would hide this mistake as a use-after-free. Enforce drop order in a type instead.
- In general, any QuickJS assertion or native bug kills the host.

**G-4. rquickjs 0.14 API notes.**
- Async closures are native: `ctx.async_with(async move |ctx| { … })`. The `async_with!` macro is `#[deprecated]`.
- Async host functions use `Function::new(ctx, Async(move |ctx: Ctx<'js>, url: String| async move { … }))`. The future must return `rquickjs::Result<_>`. It is driven only while `async_with` (or `rt.idle()`) is being polled.
- Without the `parallel` feature, `AsyncRuntime` is `!Send`. Our answer is a dedicated thread with a current-thread Tokio runtime and no `parallel` feature. `parallel` would add a global lock and `unsafe impl Send`, which a thread-per-runtime design does not need.
- The interrupt handler and memory limit are **per runtime**, not per context.
- `set_memory_limit` is a **no-op** with the `rust-alloc` or `allocator` features.
- `AsyncRuntime::idle()` reports job errors with `println!` to **stdout**. That is a protocol hazard for any stdio-JSON-RPC JS worker.

**G-5. Other QuickJS behaviour.**
- An interrupt surfaces as `Error: interrupted` (an InternalError with the uncatchable flag). `try/catch` cannot swallow it, as verified.
- OOM is an ordinary *catchable* `Error: out of memory`. The engine survives, and malloc returned to the baseline after GC.
- QuickJS checks its stack limit against the real thread stack. The JS thread's stack must be well above `max_stack_size`; we use 16 MiB against 512 KiB.

### Python worker

**G-6. Two soft-cancel mechanisms behave differently.** Both were measured.
- **Protocol `$/cancelRequest`** (portable):
  - The worker's reader thread calls `signal.pthread_kill(main, SIGINT)`.
  - It needs the GIL first. For a pure-Python CPU loop that costs the 5 ms switch interval (+6.5 ms measured).
  - It **cannot** interrupt native code that holds the GIL (bigint pow), so that case ends in a hard kill.
- **Host `kill(pid, SIGINT)`** (Unix):
  - The C-level handler needs no GIL. CPython's bigint and factorial loops call `PyErr_CheckSignals`, so they soft-cancel in 1.5 ms.
  - It requires the worker's helper threads to **block SIGINT** (`pthread_sigmask`). Otherwise the kernel may deliver the signal to the reader thread, and a `time.sleep()` in the main thread would not be woken.
- **Neither** can stop signal-deaf native code (`hashlib.pbkdf2_hmac`, most C extensions). Only the hard kill does.

**G-7. Signal-handling traps.**
- **Inherited `SIG_IGN`.** If the parent ignores SIGINT (nohup, some launchers), Python keeps `SIG_IGN` and `KeyboardInterrupt` never fires. The worker must reinstall `signal.default_int_handler` explicitly.
- **`interrupt_main()` does not wake syscalls.** `_thread.interrupt_main()` only sets a flag and does not wake blocking syscalls. `pthread_kill` does.
- **Torn frames.** A `KeyboardInterrupt` can land anywhere in the main thread, so all protocol writes go through a dedicated writer thread fed by a `SimpleQueue`. A frame is never torn.
- **Lost replies.** A stray interrupt that races with completion is caught in the main loop, which re-sends the reply. Duplicates are harmless.
- **Terminal Ctrl+C.** Workers get their own process group (`process_group(0)`), so Ctrl+C in the host's terminal does not interrupt them.

**G-8. Pipe hygiene. All of these were needed.**
- At startup the worker takes `dup(0)` and `dup(1)` for the protocol, then points **fd 1 at stderr** and **fd 0 at `/dev/null`**. `print`, `os.write(1)`, C extensions and `input()` then cannot corrupt framing or steal protocol bytes.
- The host must **drain stderr continuously**: a full 64 KiB pipe blocks the worker forever.
- The host answers worker requests from a spawned task, so the stdout reader never blocks on a stdin write.
- The worker's reader thread always drains stdin, so host writes never block either.
- Result: 2 MiB in each direction plus 1 MB of stderr went through in 12.9 ms.
- **Per-execution output state.** The `print()` capture buffers partial lines. It must be created fresh for each execution and flushed in a `finally`, so a script that fails or is cancelled after `print(…, end='')` cannot prepend its leftover text to the next script's log on the same worker. This covers the script's main thread only: a thread the script leaves running, or a module that kept a reference to an old `sys.stdout`, can still write into a later run's log. Spec 04 must decide how to handle those (for example, recycle the worker when a script leaves threads behind). Found in the Codex review; the harness now checks error-then-reuse and cancel-then-reuse.

**G-9. Core dumps dominate crash detection.**
- With `systemd-coredump`, a segfaulting worker took **~236 ms** to reap.
- `RLIMIT_CORE=0` does not prevent the dump when `core_pattern` pipes to a helper (it only got down to ~104 ms).
- `prctl(PR_SET_DUMPABLE, 0)` in the worker (via `ctypes`, ~1 ms of startup) brings detection down to **1.8 ms**. It also keeps users' journals free of core dumps from crashing scripts.
- Trade-off: debuggers and py-spy cannot attach to a non-dumpable process. Keep it as a setting.
- `faulthandler` output in the stderr tail gives a useful crash reason.

**G-10. Startup is much cheaper than estimated.**
- A worker is ready in 13.5 ms (3.15) or 15.9 ms (3.14). The bare interpreter takes about 7.5 ms. tech-stack §7.2 estimated 30-80 ms.
- Real cold-start cost will come from users' `import`s (requests, numpy), which the warm pool and its per-worker code cache hide.

**G-11. Two Pythons.**
- In a shell, `python3` resolves to mise's 3.15. The distro `/usr/bin/python3` is 3.14.8.
- A desktop-launched app usually lacks shell-rc PATH additions (mise, pyenv, conda), so it would pick a *different* interpreter than the user's terminal.

**G-12. `-I -B` flags.**
- `-I` ignores `PYTHON*` env vars and user site-packages. That is good for robustness, but `pip install --user` packages become invisible. Per-profile venvs (as planned) are the right answer.
- `-B` avoids writing `.pyc` next to a read-only resource.

## Recommendations for `docs/spec/04-scripting.md`

### JavaScript

1. **In-process QuickJS stays the default for the user's own scripts.** Its JS-bound kill latency (<0.1 ms) and memory/stack limits are good enough. Document that the deadline is "best effort" for native-heavy code (G-1).
2. **The "isolated JS worker" mode is required:** the same `JsHost` in a child process (`--worker js`), reusing the Python pool's framing, timeouts, kill/respawn and Job Object code. Use it:
   - always for imported or community scripts;
   - automatically for an action whose script overshot its deadline by more than 1 s. Show a UI warning and let the user pin it in-process.
   - Also keep a watchdog for in-process JS. It cannot kill, but it detects an overshoot, marks the thread lost, and starts a replacement thread so other actions keep running.
3. **Threading.** Run a bounded pool of dedicated OS threads (default 2, maximum `min(4, cores/2)`). Each thread gets its own current-thread Tokio runtime and a stack of 8-16 MiB. Never run JS on the shared runtime. Do not enable `parallel`.
4. **Contexts.**
   - Cache one runtime+context per action. That gives Streamer.bot parity, where state persists between runs.
   - Rebuild it after any timeout, interrupt, OOM or await-timeout (G-2). That costs only ~50 µs.
   - Store compiled functions in a type that drops `Persistent`s before the runtime (G-3).
5. **Defaults.**
   - Deadline 5 s, configurable per sub-action. The same value bounds awaits through a host-side timeout.
   - Memory 64 MiB per runtime; stack 512 KiB.
   - Never enable `rust-alloc` or `allocator`.
6. **Don't fork `rquickjs-sys`** to lower `JS_INTERRUPT_COUNTER_INIT` unless isolated mode proves too heavy. Instead, open an upstream issue asking for a time-based or "interrupt now" API. Optional follow-up.

### Python

7. **Pool.**
   - Default N=2, started lazily on the first Python execution. Configurable, with a maximum of `cores/2`.
   - Reap idle workers after 10 min. Respawning costs only ~15 ms, but reaping loses users' imported modules.
   - Queue executions when every worker is busy (a semaphore plus a queue timeout).
8. **Framing.**
   - Keep LSP `Content-Length` + JSON-RPC 2.0 over stdio as designed.
   - Make `log` and `print` **notifications**, not requests: each request costs about 20 µs of round trip. `globals.get` has to stay a request.
   - Error codes: `-32800` cancelled, `-32000` script error, `-32601` unknown method.
   - All per-execution worker state (print capture, `sys.stdout`, namespace) is created per execution and flushed or discarded on every exit path, success, error and cancel alike, before the reply is sent (G-8). Spec 04 should require an error-then-reuse test.
9. **Timeouts.**
   - Soft deadline 5 s, then a **grace of 1 s**. Soft cancel lands in 1-7 ms, so the grace only needs to cover user `finally` blocks.
   - Then hard kill and respawn.
   - Cancel by `kill(pid, SIGINT)` on Unix (helper threads block SIGINT). Use `$/cancelRequest` + `interrupt_main()` on Windows (G-6).
10. **Worker hardening checklist** (all implemented in the spike):
    - fd 0 and fd 1 redirection;
    - explicit `SIGINT` handler;
    - reader and writer threads;
    - `faulthandler` to stderr;
    - non-dumpable on Linux, with a "debuggable workers" opt-out;
    - `RLIMIT_AS`, default 2 GiB. The spike used 1 GiB; numpy/BLAS reserve large virtual address space, so 2 GiB is a safer default. Consider `RLIMIT_DATA` as well;
    - exit on stdin EOF;
    - its own process group;
    - a continuously drained stderr, with a 64-line tail attached to crash errors.
11. **Orphans.**
    - Stdin EOF covers a host crash only while the worker's reader thread can get the GIL.
    - Add `PR_SET_PDEATHSIG(SIGKILL)` in a `pre_exec` on Linux. It was not tested in this spike.
    - Use a Job Object on Windows (below).
12. **Provisioning.**
    - Resolve the interpreter once, store its **absolute path and version** in settings, and show both. Never rely on the GUI process's PATH (G-11).
    - Keep the plan's order: user path → system `python3` ≥ 3.10 → managed python-build-standalone.
    - Ship the worker as a read-only resource run with `-I -B`. Put per-script requirements into a per-profile venv.
    - Startup cost is no longer a reason to bundle Python.

## Windows design note (not tested)

- **Job Object per pool.** Create one with `CreateJobObjectW`. Set `JOBOBJECT_EXTENDED_LIMIT_INFORMATION` with:
  - `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`: workers die with the host's job handle, so no orphans even on a host crash;
  - `JOB_OBJECT_LIMIT_PROCESS_MEMORY`: the `RLIMIT_AS` equivalent; the worker's `resource` import fails on Windows and is skipped;
  - `JOB_OBJECT_LIMIT_ACTIVE_PROCESS`: stops fork bombs;
  - optionally `JOBOBJECT_CPU_RATE_CONTROL_INFORMATION`.
- **Assigning workers to the job.**
  - Nested jobs are allowed since Windows 8, so this works even when a launcher already put the host in a job.
  - Call `AssignProcessToJobObject` right after spawn, before the first `execute`. The worker runs no user code before `ready`, so the race is harmless. The alternative is `PROC_THREAD_ATTRIBUTE_JOB_LIST`, which needs raw `CreateProcessW`.
  - Candidate crates: `windows`/`windows-sys` (already in the tree via tokio) or `win32job`.
- **Process creation flags** (`CommandExt::creation_flags`):
  - `CREATE_NO_WINDOW`: no console flash for a GUI host;
  - `CREATE_NEW_PROCESS_GROUP`: the counterpart of `process_group(0)`. It disables Ctrl+C in the child group, so a dev console's Ctrl+C does not reach workers.
- **Soft cancel.** Do **not** rely on `GenerateConsoleCtrlEvent`: it needs a shared console, which a Tauri GUI host does not have. Use `$/cancelRequest` → `_thread.interrupt_main()`.
  - **To verify on Windows:** whether `interrupt_main()` wakes `time.sleep()` there. CPython's Windows sleep waits on the SIGINT event, which `PyErr_SetInterruptEx` may not set.
  - The hard kill (`TerminateProcess` via `Child::start_kill`, or `TerminateJobObject` for the whole tree) covers the rest.
- **Already portable in `den_worker.py`:**
  - `faulthandler` (it reports access violations);
  - `os.dup2` on CRT fds;
  - binary-mode stdio;
  - the `pthread_sigmask` and `pthread_kill` calls, which are guarded by `hasattr`.
