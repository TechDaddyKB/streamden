| 2026-10-19 | D-059 | **Service onboarding default: browser authorization first, manual connection as the fallback.** Wherever a provider supports it, StreamDen connects a service by sending the user to the provider's own sign-in and consent page in the system browser (device-code or loopback-PKCE OAuth, or the provider's official "Sign in with …" program) against a StreamDen-registered developer app, so the user never copies IDs, secrets or tokens. Manual connection (pasting a token, key or URL; bringing your own developer app) stays available as an **advanced** option and is the *only* path where the provider offers nothing else. The order amends the manual-first wording of **D-031** (YouTube: the shared StreamDen project is the default sign-in path, usable for limited test use before Google verification and for the public after it; bring-your-own project is the advanced fallback and the supported path while the shared production sign-in is unavailable) and of D-046/D-021 only where a browser flow actually exists. Where a provider's OAuth needs a confidential secret (Kick, Discord `webhook.incoming`, Streamlabs, StreamElements, Patreon, Shopify merchant authorization), browser consent through the hosted relay's token broker is the preferred target and the manual paste is the interim default until app approval and the broker exist. It does **not** promise OAuth a provider does not offer (Anthropic subscription login, Rumble, TikTok), does not bypass provider approvals, verification, quotas or secret requirements, and does not move the hosted-relay milestone (D-019, still "later"; its timing is Q-C12).
